## 2.Tracing为什么要引入缓冲区

我们都知道，在一个运行的系统中，日志的存在必不可少，从基本运行信息，到任务执行情况，再到异常追踪与记录，这些都离不开日志，这也是Tracing系统最基本的形式

为了方便事后追踪查阅，日志常常选择落盘到磁盘上进行持久化，但是这也引来一个问题

对于高频次的流式日志，在较为大型的系统下，每秒就可能有上百条日志产生，此时我们需要即时地将这些日志写入磁盘，而出于对计算机存储层次结构的了解，我们知道磁盘读写相较于正在RAM内运行的程序执行速度来说是很慢的，这样长期运行下去，就可能出现一个情况，有大量的日志堆积，处于待处理写入磁盘状态，从而造成庞大的磁盘I/O压力，进而导致运行卡顿，这就是典型的监控系统崩溃从而拖垮业务的场景

为了避免这个问题，我们引入内存缓冲区，这个的作用就可以类比介于电商平台和数据库之间的Redis或者Kafka，通过队列实现一个削峰填谷的作用，降低数据库的读写压力

缓冲区还实现了一个异步解耦的功能，一条日志我不需要立刻在当前线程中同步落盘阻塞业务，先放到缓冲区中，然后缓冲区在后台挂一个独立线程去进行异步写入，这样就算Tracing系统挂了，也不影响正常业务的进行

## 3.进一步思考：为什么需要环形

一般来说我们实现一个普通链表队列作为缓冲区，来一条日志，创建一个新节点，接到后面，写入一条日志，头节点向后挪，原来的头节点删掉

这样就带来了一个新的问题，如果对C++有一定了解，就会知道这种频繁的内存申请与释放，即`malloc`和GC会带来性能抖动，特别是在日志吞吐量较大的场景，很容易造成OOM或者其他崩溃，另外链表的不连续内存结构也会拖慢访问和遍历

首先连续型，为了避免零零散散的内存分布，我们需要开辟一整块的内存空间；其次频繁内存分配，我们需要在一开始就申请固定大小的内存，而循环队列完美地解决了这个问题

在循环缓冲中，我们用两个指针来维护读写位置，一个写指针指向下一个要被写入新数据的位置，在这里就是新产生的日志被塞进缓冲区；一个读指针指向下一个要被读取的数据的位置，在这里就是即将从缓冲区写入磁盘的日志

当写指针追伤读指针的时候，就说明缓冲区满了，这里就要运用到另一个设计思想：Lossy覆盖写

我们直接用最新的日志覆盖掉那条还未来得及写入磁盘的日志，从而保证现场最新的那几毫秒的数据，而不是再开拓新空间，将整个系统拖入OOM的深渊

接下来来看我的Tomato-Router中是如何实现环形缓冲的：

```rust
pub fn push(&self, line: LogLine) {
    let mut inner = self.inner.lock().expect("log buffer mutex poisoned");

    while inner.lines.len() >= inner.capacity {
        inner.lines.pop_front();
        inner.dropped = inner.dropped.saturating_add(1);
    }

    inner.lines.push_back(line);
    inner.version = inner.version.wrapping_add(1);
}
```

这里就是一个获取互斥锁，检查容量并移除旧日志，递增移除数，新日志添加到队尾，递增版本号，释放锁的过程，然后`while`主要实现的是一个防御性

然后暂时还没做持久化日志落盘，这里是让TUI的Logs页面做消费者，每tick渲染时读取缓冲区消费

## 4.实际设计

### 4.1.单调递增序列号以及位掩码

对于初级环形缓冲，可能会使用普通的维护`head`和`tail`指针，然后计算取模来实现循环队列，但是在高性能系统中，取模运算在底层CPU需要做昂贵的除法指令，周期极长，所以我们采用单调递增64位序列号+位掩码来实现循环缓冲

具体来说，有以下公式：

$$
\text{Index} = \text{Sequence} \& (\text{Capacity} - 1)
$$

其中 $\text{Capacity} = 2^{n}$

这个计算索引的原理就是当模数是 $2^{n}$ 时，对其求余在二进制上就相当于截取低位，这个 $\text{Sequence}$ 就是我们前面所说的单调递增的64位序列号

通过这种方式计算索引，按位与的计算速度要比取模快得多，从而能够提升Tracing系统的效率

---

### 4.2.SPSC：无锁队列与内存序

接下来我们分两种情况讨论生产者和消费者的对应关系以及缓冲区的具体实现

首先是SPSC，即单写单读，一个生产者对应一个消费者，比如一个主线程写日志，一个后台异步线程落盘

在这种情况其实我们甚至不需要`mutex`互斥锁，直接靠原子变量的Acquire-Release语义就能实现轻量的效果

```rust
use std::sync::atomic::{AtomicU64, Ordering};

pub struct SpscRingBuffer<T, const CAP: usize> {
    buffer: [T, CAP],
    head: AtomicU64,
    tail: AtomicU64,
}

impl<T, const CAP: usize> SpscRingBuffer<T, CAP> {
    pub fn push(&self, value: T) -> Result<(), T> {
        let head = self.head.load(Ordering::Relaxed);
        let tail = self.tail.load(Ordering::Acquire);

        if head - tail >= CAP as u64 {
            return Err(value); // 如果是Lossy模式，这里可以直接做覆盖
        }

        unsafe {
            let p = self.buffer.as_ptr().add((head & (CAP as u64 - 1)) as usize) as *mut T;
            p.write(value);
        }

        self.head.store(head + 1, Ordering::Release);
        Ok(())
    }
}
```

首先讲讲，在这种场景下，我们担心的是什么

在单线程中，编译器和CPU都会为了性能优化，做一些“自作聪明”的事情，在不改变单线程执行结果的前提下，私自调换指令的执行顺序，这个就叫做**指令重排**

- **编译器重排**：以Rust为例，在生成机器码的时候，编译器觉得先执行B再执行A效率更高，就直接在编译期替换了
- **CPU乱序执行**：现代CPU拥有乱序执行引擎和写缓冲区，哪怕编译器没有调换顺序，CPU为了填满流水线，也会把后面的内存写入提前执行

但是在多线程无锁并发中，这种自作聪明是致命的

举个例子，我们把上面的代码中的所有`Ordering`语义都换成最松散的`Relaxed`

生产者线程执行到这一行：

```rust
p.write(value);
```

由于CPU的写缓冲区存在，这行代码的数据可能还卡在CPU的Store Buffer里，还没同步到主存或L3缓存

紧接着生产者执行

```rust
self.head.store(head + 1, Ordering::Relaxed);
```

因为是`Relaxed`，编译器和CPU觉得这两行之间没什么逻辑依赖，于是顺序颠倒，或者CPU先把`head`的更新广播出去了

此时消费者线程在另一边读到`head`变了，说明有新数据，随即去读`buffer`对应槽位的数据，结果独到的是旧的垃圾数据或者未初始化的内存，引发数据可见性灾难

而这里通过写端的

```rust
self.head.store(head + 1, Ordering::Release);
```

确保所有在`store(Release)`之前发生的内存读写操作，绝对不准重排到这个`store`的后面

然后读端

```rust
let tail = self.tail.load(Ordering::Acquire);
```

让所有在`load(Acquire)`后面发生的内存读写操作，不重排到这个`load`的前面

这样一来，两者配合，生产者用`release`把数据写入固定在指针更新之前，消费者用`Acquire`确保读到更新的指针之前，绝对不会去读缓冲区的数据

### 4.3.MPSC：多线程抢占与乱序写入

到了MPSC，即多生产者单消费者，就让人眼前一黑了，多个线程争夺写入权，最直接的想法是通过`atomic_fetch_add(&head, 1)`来抢占槽位

但是这也有一个问题，我们来看一个例子：

假设容量为4，线程A抢到了索引`0`，线程B抢到了索引`1`

由于操作系统的神秘线程调度顺序，线程B虽然拿到的索引靠后，但他更快地把数据写入了槽位`1`，而线程A因为被系统中断了，迟迟没有把数据写入槽位`0`

此时消费者去读队列，看到索引`0`为空，这就是多线程并发下的乱序写入

我们这里列出两个方案来尝试解决这个问题：

---

#### 4.3.1.两阶段提交

每个槽位不仅存数据，还配一个状态标记

1. **Claim**：线程通过`fetch_add`拿到槽位索引
2. **Write**：往槽位里面填数据
3. **Commit**：写完后，把该槽位的状态原子变更为已就绪

对于消费者，只能按顺序读，如果发现当前头部的槽位还没commit，只能短暂自旋等待

---

#### 4.3.2.Sequence Barrier

两阶段提交成功解决了消费者怎么知道数据写完了的问题，但它同样带来了两个新的问题：每个槽位都要维护状态，槽位复用时还需要重置；消费者需要自己扫描状态位才能找到连续可读的前缀

在这里，我们不妨来看看著名的Java高性能并发框架Disruptor是如何解决这个问题的

它不再去问某个槽位能不能读，而是看逻辑上已经连续发布到哪个时刻，这就是Sequence Barrier的核心所在

Disruptor维护一条全局单调递增的序列号，第 $i$ 条消息放在 $i \& (\text{Capacity} - 1)$ 的位置

生产者分三步来写，这里其实和两阶段提交有点像

1. **Claim**：用一个原子加法申请一段序列号
2. **Write**：往对应的槽位里填数据
3. **Publish**：写一个发布标记

这里有一个特别的点就是发布标记，它不是只存一个布尔值，如果只存这个布尔值，那么槽位复用的时候就必须要清零，否则上一圈留下的`true`会让消费者误以为新数据已经就绪

它存的是圈数，让标记携带版本：

```java
flag = sequence >>> log2(capacity)
```

也就是这个槽位被第几圈写过，消费者用当前序列号算出期望圈数，和数组里的值比较，如果对不上就说明这里的值还是旧的

这其实就是一个epoch标记，用很小的代价解决了环形缓冲的ABA问题，槽位复用的时候，旧标记失效而无需额外清理

对于消费端，它用`SequenceBarrier.waitFor(sequence)`完成两件事：

1. 等进度：等到生产者游标或者上游消费者的最小进度至少到达请求的序列号
2. 查连续性：从请求的序列号开始，沿着发布标记逐个检查，遇到第一个未发布的位置停下

拿一个例子来看：

```txt
序列号:   4      5      6      7
状态:    done   ?     done    ?
cursor:                 6
可读上界: 4
```

假设容量为8，生产者A抢到5，生产者B抢到6，然后B先写完发布，A被调度器挂起了，此时生产者的claim游标已经是6,5还没有发布

我们不难发现，它实际上就是两阶段提交的Pro版，只是多了一个barrier用来找出连续commit的前缀

如果只有上面这些，那么这个策略可能叫Commit Barrier更加合适，但是它牛逼的地方就在于可以负责依赖协调

一个Disruptor可以有多个消费者，消费者之间有依赖，比如从解析到过滤再到落盘，下游的barrier不是直接等待生产者，而是等待上游消费者的进度，如果有多个消费者，就取上游进度最小值

我们可以看到，现在讲的已经不局限于日志系统，更像是一种生产-消费协同的处理范式，对于广泛的业务场景都有参考性
